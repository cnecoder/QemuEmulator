# 部署文档 —— ARM64 + USB 蜂窝模块模拟环境

> 版本：v1.0（2026-11）。面向负责搭建环境的工程师/运维。
> 三种部署形态：A. 单机开发环境（WSL2 或 Linux + Docker）；B. CI 容器（无 docker 依赖）；C. 多设备集群。

---

## 1. 前置条件

| 形态 | 宿主要求 | 说明 |
|---|---|---|
| A（标准） | x86_64 Linux 或 WSL2；Docker；≥8C/8GB（推荐 16C/32GB）；磁盘 ≥15GB；外网可达 github/download.qemu.org/archive.ubuntu.com | 不需要 KVM |
| B（CI 容器） | 任意能跑 Docker 的 x86_64 环境（容器内 TCG 运行） | `QEMU_DIRECT=1` |
| C（集群） | 同 A，资源 ×N（每设备 4 vCPU/2GB） | 双设备验证约 8 vCPU |

软件组件版本（当前 pin）：Ubuntu 26.04 容器基座、QEMU 11.1.3（源码编译 + usb-wmodem 设备）、edk2 2024.02 固件（仓库内置 `p1/compat/QEMU_EFI.fd`）、guest Ubuntu 24.04 ARM64 云镜像。

## 2. 形态 A：单机标准部署

### 2.1 步骤

```bash
# 1. 克隆
git clone git@github.com:cnecoder/QemuEmulator.git && cd QemuEmulator

# 2. 构建容器镜像
docker build -t p1-qemu-build -f p1/docker/Dockerfile.build p1/docker   # 编译+运行时（26.04）
docker build -t p0-qemu      -f p0/docker/Dockerfile      p0/docker     # seed 生成等辅助

# 3. 下载云镜像（588MB，自动 SHA256 校验）
mkdir -p p0/images && bash p0/scripts/01_fetch_image.sh p0/images

# 4. 下载 QEMU 源码并编译（版本参数化；产物自动复制到 p1/build/qemu-custom/）
curl -fL -o p1/src/qemu-11.1.3.tar.xz https://download.qemu.org/qemu-11.1.3.tar.xz
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/p1":/work -w /work \
    p1-qemu-build bash scripts/10_build.sh        # 约 10-15 分钟

# 5. 拉起环境（启动 + 等待 + 置备；首次置备含 guest 内安装，10-30 分钟视网络）
python3 p1/envctl.py up --fresh

# 6. 验收
python3 p1/envctl.py verify                     # 设备级 15 断言 → P1_ALL_GREEN
python3 p1/envctl.py test                       # 全量回归 32 例 → 32 passed

# 7. 打稳定快照（强烈建议）
python3 p1/envctl.py snap stable
```

### 2.2 首次置备说明（重要）

- 全新 overlay 的首次 `up` 中，cloud-init 会执行 `apt update` + 安装
  `linux-modules-extra-generic` / `isc-dhcp-client`（seed 的 packages 列表）——
  **在 TCG+slirp 下可能需要 20-30 分钟**。这是每份全新 overlay 的一次性成本。
- 加速替代：在已置备的 overlay 上打快照，之后 `envctl.py restore stable` 秒级进入就绪态；
  或克隆已置备 overlay 作为其他设备的起点（集群脚本即此策略）。
- 若 cloud-init 的安装失败（网络抖动），VM 仍可 SSH：手动
  `envctl.py provision`（其内置按需安装+重试），完成后重跑 verify。

### 2.3 部署验证清单

| 检查 | 命令 | 期望 |
|---|---|---|
| QEMU 版本/设备 | `docker exec p1-vm /home/luo/Project/Emulator/p1/build/qemu-custom/qemu-system-aarch64 --version`（容器内执行） | QEMU 11.1.3 |
| 设备注册 | `envctl.py verify` | P1_ALL_GREEN |
| 快照 | `envctl.py snap t1 && envctl.py restore t1` | 各自秒级完成 |
| 回归 | `envctl.py test` | 32 passed |
| 场景 | `envctl.py scenario no_sim && envctl.py at "AT+CPIN?"` | 含 `+CME ERROR: 10` |

## 3. 形态 B：CI 容器部署（无 docker 依赖）

```bash
# 构建 CI 镜像（多阶段：容器内编译 QEMU 11.1.3）
docker build -t qemuemulator-ci -f ci/Dockerfile .

# 运行全量流程（镜像获取→冷启动置备→回归）
docker run --rm --network host -v "$PWD":/lab qemuemulator-ci bash /lab/ci/run_ci.sh
```

要点：
- 容器内使用 `QEMU_DIRECT=1`：QEMU 以普通进程直跑（无 docker-in-docker）。
- 缓存：将宿主的 `p0/images/` 与 `p1/run/` 挂载进容器可跳过下载与置备：
  `docker run ... -v "$PWD/p0/images":/lab/p0/images -v "$PWD/p1/run":/lab/p1/run ...`
- `.github/workflows/ci.yml` 提供 workflow_dispatch 入口（junit 产物上传）。
  **状态：配方已就绪、未在真实 Actions 上验证过**；首跑预计 40-60 分钟。

## 4. 形态 C：多设备集群部署

```bash
# 拉起（两台设备 + 两条链路 + 损伤代理 + 各自场景引擎 + 置备 + 链路 IP）
bash p1/scripts/30_cluster_up.sh

# 验收（基线连通 / 时延损伤独立性 / 丢包损伤独立性 / 双蜂窝通道）
bash p1/scripts/28_cluster_check.sh        # 期望 CLUSTER_ALL_GREEN

# 链路损伤操作（link1/link2 完全独立）
python3 p1/cluster/link_ctl.py set link1 --delay 200 --jitter 20
python3 p1/cluster/link_ctl.py set link2 --loss 30 --bw 1000
python3 p1/cluster/link_ctl.py status
python3 p1/cluster/link_ctl.py clear link1
python3 p1/cluster/link_ctl.py clear_all

# 回收
bash p1/scripts/31_cluster_down.sh
```

拓扑与地址规划（修改需同步 `30_cluster_up.sh` 与使用方）：

| 项 | 设备 A | 设备 B |
|---|---|---|
| 容器/SSH | p1-vm-a :2223 | p1-vm-b :2323 |
| 套接字 | qmp-a / at0-a / engine-a | qmp-b / at0-b / engine-b |
| overlay | run/disk-a.qcow2 | run/disk-b.qcow2（克隆自 A） |
| link1 | 10.0.100.1/24（MAC 52:54:00:a1:00:01） | 10.0.100.2/24（52:54:00:b1:00:01） |
| link2 | 10.0.200.1/24（52:54:00:a2:00:01） | 10.0.200.2/24（52:54:00:b2:00:01） |
| UDP | 发 4001/4003，收 4101/4103 | 发 4002/4004，收 4102/4104 |
| 蜂窝数据面 | 各自独立 slirp 10.0.3.0/24（DHCP 10.0.3.15） | 同左 |

扩展到 N 设备：`30_cluster_up.sh` 的设备表加行（新 SSH 端口/MAC/overlay/端口对），
`links.json` 加链路组；wm_linkd 与测试脚本天然支持。

## 5. 升级与回滚

### 5.1 QEMU 版本升级
1. `curl -fL -o p1/src/qemu-<新版本>.tar.xz https://download.qemu.org/qemu-<新版本>.tar.xz`
2. `QEMU_VER=<新版本> docker run ... 10_build.sh`（编译失败按报错适配 dev-wmodem.c——
   参考 9.2→11.1.3 的适配面：include 布局、CharFrontend、class_init const、
   Property 数组 const 且无 END_OF_LIST）
3. 冒烟：`envctl.py up`（不 --fresh）+ `envctl.py verify`
4. 全绿即完成；异常则 `git checkout p1/device/` 回滚设备模型并维持旧版本
   （旧二进制在 `p1/build/qemu-<旧版本>/build/` 仍可用，将 qemu-custom 指回即可）。

### 5.2 固件更换
1. 新固件 .deb 下载后容器内解包，提取 QEMU_EFI.fd 覆盖 `p1/compat/QEMU_EFI.fd`
2. 冒烟：直接启动看串口是否越过 UEFI banner（DXE/BdsDxe 行出现）
3. 已知坑：edk2 2025.11（26.04）在 QEMU 9.2/11.1.3 上挂死——升级固件前务必双版本验证

### 5.3 golden 镜像更新
1. `01_fetch_image.sh` 下载新版
2. overlay 全部重建（`rm p1/run/disk*.qcow2`），置备重来；旧 overlay 可 `qemu-img rebase -u` 迁移 backing 路径

### 5.4 overlay 迁移（换目录/换机器）
```bash
qemu-img rebase -u -b <新golden绝对路径> -F qcow2 <overlay路径>
```

## 6. 部署排错索引

部署阶段的高频故障（症状→根因→处理）集中在 README.md §9 的 18 项 FAQ 表，
按出现阶段索引：

| 阶段 | 高发问题 |
|---|---|
| 镜像构建 | —（容器构建稳定） |
| QEMU 编译 | QEMU 新版本 API 变化（见设计文档 §3.1.4）；include 布局 |
| 首次启动 | 缺 qemu-xhci；ROM 缺失（`-global virtio-pci.romfile=`）；固件挂死（换 pin 固件） |
| 置备 | usbtouchscreen 抢占；假文件遮蔽；重枚举未完成写 new_id（均已被置备脚本自动处理） |
| 数据面 | 双 slirp 同网段（已独立网段）；dhclient 缺失（已入 seed） |
| 快照 | pflash 不支持快照（已用 -bios 规避）；VMSTATE_USB_DEVICE（已包含） |
